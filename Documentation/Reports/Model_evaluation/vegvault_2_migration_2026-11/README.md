# Stage V VegVault 2.0.0 migration: evidence (November 2026)

Evidence produced while moving the project from VegVault 1.0.0 to VegVault 2.0.0, following `Documentation/Implementation_plans/2026-11-25_vegvault_2_migration_plan.md` (part of [#180]). Every query opened the database files read-only. No production store was rebuilt. The 1.0.0 file is kept as `Data/Input/VegVault_1.0.0.sqlite` for the comparisons.

## Release record (step V1)

- Every pipeline now reads the VegVault release from the database file on each build (target `config_vegvault_release`: version, build commit and build manifest hash). Replacing the file therefore marks the extraction targets as outdated, and the store validator reports the change.
- The accepted 2.0.0 file reports version 2.0.0, commit `f19d588` and manifest hash `94516fdf…`. Its SHA-256 (`559577c7…`) matched the release check of 25 November 2026.
- The CZ trial run (`R/03_Supplementary_analyses/Testing/Smoke/run_cz_pipelines.R`) completed on 2.0.0. The CZ fossil-pollen window holds 56 datasets in 2.0.0 against 47 in 1.0.0, and 1,343 fossil samples with age uncertainty against 972. The CZ modern window holds 2,318 plot datasets against 2,320. The 1.0.0 trial stores are kept in `Data/Temp/vegvault_2_migration/cz_stores_vegvault_1_0_0/`.

## Extraction on vaultkeepr 0.2.0 (step V2)

- **Empty windows.** vaultkeepr 0.2.0 builds an empty query instead of stopping when a window holds no data. The project's own record check still raises the typed `biodynamics_vegvault_no_records` condition for every case tried: open ocean, a window with datasets but no samples in the age range, and a window without vegetation plots. The Eastern Siberia window (unit `as_r006`) that the tests used as an empty fossil-pollen window holds two fossil-pollen datasets (77 samples) in 2.0.0, so the test now uses a central Sahara window.
- **Age uncertainty.** `extract_age_uncertainty_from_vegvault()` returns the same columns (`dataset_name`, `sample_name`, `iteration`, `age_uncertainty`) and 1,000 iterations per sample. Fossil sample names now carry the Neotoma dataset id (`fossilpol_<Neotoma dataset id>_<level>`).
- **dbplyr version.** vaultkeepr 0.2.0 needs dbplyr 2.6.0 or newer: with dbplyr 2.5.0, its filters on selected ids produce invalid SQL and `get_age_uncertainty()` stops. The project now pins dbplyr 2.6.0; reported as [vaultkeepr#79].
- **Trait extraction time.** Raw extraction on 2.0.0 took 203 s for America (8.7 million records), 76 s for Europe and 72 s for Asia, so one run per continent is affordable without a change to vaultkeepr. About 70 s of each run is the full join of the trait table that `get_traits()` builds when taxon names stay original ([vaultkeepr#77]). The 1.0.0 times (591 s for America, 5 s for Europe, 3 s for Asia) time the whole continental loader, including the completeness filter and taxon names, so they are not directly comparable. The America window holds almost the same number of records in both releases (8,713,468 in 1.0.0, 8,711,891 in 2.0.0).
- **Trait data sources.** The America extraction stopped after 211 s on the project's check that every trait record has one data source. In 2.0.0, 3,609 BIEN trait datasets (7,869 plant height values, 3,604 of the datasets in the America window) have no data source, because their BIEN records name no provider. VegVault 1.0.0 linked the same records to a data source with an empty description (id 616): every one of these datasets with coordinates lies at the coordinates of a 1.0.0 dataset of that source, and of no other. 2.0.0 leaves the link empty, and the accepted file stays as it is ([VegVault#167]; the issue first read this as lost links, which the reply there corrects). `load_trait_records_from_vegvault()` therefore now keeps trait records without a data source, with `data_source_id` `NA`, and still stops when a record's dataset is missing from `Datasets` or appears twice. With this change the America window loads completely: 8,711,891 records, of which 6,653 (in 3,604 datasets, all plant height) have no data source.
- **Trait call.** `load_trait_records_from_vegvault()` now asks vaultkeepr for original taxon names explicitly (`classify_to = "original"`). vaultkeepr 0.2.0 reads the previous `NULL` the same way, so the records do not change.
- **Outdated supplementary scripts, left as they are.** `R/03_Supplementary_analyses/Prediction/Predict_from_model.R` uses the 1.0.0 ids for the gridpoint source type and two climate variables and opens the database writable. `R/03_Supplementary_analyses/Age_uncertainty_exploration_2026-05-04.R` calls `build_vegvault_plan()` without the release record that the function has required since step V1. Neither is part of the rebuild.

## Trait units (step V3c)

- **One unit per domain.** `TraitsDomain` of the accepted 2.0.0 file lists six trait domains, each with one unit: diaspore mass in mg, leaf area in mm2, leaf mass per area in mg/mm2, leaf nitrogen content per unit mass in mg/g, plant height in m, and stem specific density in g/cm3.
- **Unit rules on every value.** All 10,920,952 trait values of the file carry a unit-conversion rule. In five domains, the standardised unit of every rule is the domain unit. All 276,786 leaf mass per area values are first standardised as specific leaf area (mm2 mg-1, 21 conversion rules) and then carry the derivation rule `sla_to_lma`, whose output unit is mg/mm2.
- **Unit table.** `Data/Input/Trait_corrections/VegVault_2_0_0/trait_domain_units.csv` records these six units, copied from `TraitsDomain` with a read-only query. Its build reference is the manifest hash of the release record. Its status is `source_standardised` for five domains and `source_derived` for leaf mass per area. Ondřej approved the six rows on 26 November 2026.
- **Unit column lost in extraction.** The first 2.0.0 trait store (`Data/Temp/vegvault_2_migration/traits_reference_v2/`) stopped at `validate_trait_domain_units()`: its 8,945,850 records carry `conversion_rule_key` and `derivation_rule_key` but no `trait_unit`. In vaultkeepr 0.2.0, `get_traits()` adds `trait_unit`, and `select_traits_by_domain_name()` then joins the whole `TraitsDomain` table, which also holds `trait_unit`; the query returns `trait_unit.x` and `trait_unit.y`, and the project keeps neither. Reported as [vaultkeepr#80]. Fixed in vaultkeepr 0.2.0, released on 27 November 2026 (tag `v0.2.0`, commit `cb215cf`), which is the pinned commit `4a65799` plus this fix, the dbplyr requirement of [vaultkeepr#79] and documentation. The project now pins the tag (`renv.lock`). The rebuilt trait store passes the unit check: all 8,945,850 records carry the unit of their domain. The raw review candidates and every output of the raw sorting are unchanged, including the proposal file (SHA-256 `239c7bce…`).

## Retirement of the v1 trait corrections (step V3e)

- **Source rules.** All ten VegVault 1.0.0 source-scale rules are `fixed_at_source`: VegVault 2.0.0 applies each rule's factor itself, with scale exponents between 0.99 and 1.00 over 13 to 995 shared taxa per source. The four leaf area sources reported in cm2 are converted to mm2 (source ratio 100, reference ratio 1.03). The five plant height sources were the only ones in m while the rest of 1.0.0 was in cm; 2.0.0 is in m throughout (source ratio 1, reference ratio 0.01). Stem specific density of BAAD is divided by 1,000 at the source. No 2.0.0 source-scale rule is needed.
- **Review decisions.** 29 of the 57 v1 `scale` decisions would still select 279 records in 2.0.0, and scale them a second time; dropping them was right. All 20 v1 `exclude` decisions still find their 15,865 non-positive values in 2.0.0; the automated sorting proposes such exclusions again from the 2.0.0 data.

## Raw review queue (step V3f)

- **Candidates.** The raw review queue of 2.0.0 holds 5,223 candidates, against the 3,500 to 4,300 that the plan estimated. Leaf mass per area contributes 1,646, of which 1,135 were in the part of the v1 review that was never finished.
- **Automated sorting.** `run_trait_review_vegvault_2_0_0_triage.R` gives 5,172 candidates (99%) an automated proposal: 5,125 `none` and 23 `exclude` from the policy, 23 `none` and 1 `exclude` from the interim closure. All are proposals; none is approved.
- **Human queue.** 51 candidates remain. In each, one source differs from the others of the same taxon by a factor that looks like a unit error. For one, the review submission's scale factor is corroborated by a source pair and is offered as a suggestion; the other 50 have no proposal.

## Taxon classification (step V4)

- **Coverage.** The diagnostic checked 16,356 names: every taxon name of the continental windows (fossil pollen 0 to 20 ka, vegetation plots at 0 ka, traits) that has a recorded value, plus the families and parts of the combined pollen types. The auxiliary table or the taxospace cache covers 16,154 of them. Of the other 202, the online lookup classifies 176 (169 taxon names of the windows and 7 families or parts), and 26 taxon names stay unclassified; the pipelines would stop on these.
- **Records without a value.** `vaultkeepr::extract_data()` drops records without a value, so their names never reach the classification. This matters for America vegetation plots: in both releases, 18,520 of the 29,701 plots in the window hold only presence records without an abundance (VegBank and CVS, two BIEN sources), and the extraction returns them with an empty community. A first run of the diagnostic counted these records and reported 2,291 unclassified America plot names; none of them reaches the pipeline. See the step V5 section.
- **Unclassified names.** Five are fossil-pollen names qualified with "Cf" (for example "Cf Ulmus Sp", 17 samples), all new in 2.0.0. Twenty-one are trait names, most of them misspelt ("Tacetum vulgare", "Gphalium uliginosum") or not identified to a vascular plant ("Moss", "Composite sp"), from seven data sources. All 21 are in the raw 2.0.0 trait records and none was in the v1 records, so the trait pipeline would stop on them at step V3f-4 unless they are classified first.
- **Cache spelling.** Fourteen names shared a cache file with another spelling, because the cache file name replaces punctuation and Windows file names ignore case: "Quercus Petraea" read the file of "Quercus petraea" and stayed unclassified. `load_taxa_classification()` now returns such a file under the requested name, so these names are covered.
- **Combined pollen types.** 46 of the 116 combined types are in the windows. Four already carry the 2.0.0 placement.
  - 27 would move to the family VegVault 2.0.0 assigns, with no genus (14,079 sample records). Among them are "Ostrya Carpinus" (9,206), "Ostrya Carpinus Orientalis" (1,514) and "Juniperus Thuja" (1,472), which taxospace now places at their first genus. The higher ranks come from the project's classification of the family name.
  - 15 have genera (or families) in different families, and VegVault 2.0.0 leaves them unclassified (1,853 sample records). The plan proposed the same; Ondřej chose on 27 November 2026 to place them at the lowest rank their parts share instead, as the four existing auxiliary rows of such types already do ("Betula Myrica" at Fagales, "Cupressaceae Taxaceae" at Cupressales). This keeps their counts. "Corylus Myrica" (1,010), now at *Corylus*, goes to Fagales; "Rhamnus Vitis", "Quercus Cercocarpus", "Fagus Nyssa", "Rhamnaceae Vitaceae" and "Oleaceae Brassicaceae" share only the class Magnoliopsida, which already holds "Rhamnaceae Vitaceae Undiff". At genus and family resolution such types become coarse taxa such as "Fagales" or "Magnoliopsida". The four existing rows are kept.
  - The 38 rows that change a classification (27 family rows and 11 shared-rank rows) are in `taxa_combined_pollen_types_auxiliary_rows_proposed.csv`. No auxiliary row has been added yet; Ondřej reviews the table first.
- **Draft rows for unclassified names.** For each of the 26 unclassified names, and for "Ostrya Carpinus Orientalis-Type" (a combined type that VegVault's list lacks and the lookup placed at *Ostrya*), `taxa_unclassified_names_draft_rows.csv` gives the names the entry most likely means and a draft row at the lowest rank they share. "Cf" entries go to their genus, as the auxiliary table already does. Five trait names from one source have lost the letters "na" ("Tacetum vulgare" for *Tanacetum vulgare*), which makes their reading secure. Entries whose readings share no family, and "Moss", get a row with every rank empty, which drops them from the analyses. Confidence: 18 high, 5 medium, 4 low.

## The project windows in both releases (step V5)

- **Method.** The same read-only SQL runs on both files, for the three continental windows of `spatial_grid.csv` (the temporal profiles use the same windows): fossil pollen from 0 to 20,000 cal yr BP, vegetation plots at 0 cal yr BP, and all trait datasets. The counts on 1.0.0 reproduce the v1 pipelines: 4,856 taxon names of America vegetation plots, as in the v1 America modern store, and 26, 22 and 1 cores at 0 ka in Europe, America and Asia, as in the Stage A report. These results replace the release checks planned for the first step of the rebuild.
- **Fossil pollen.** 2.0.0 holds more fossil-pollen records in every window: Europe 806 datasets and 63,505 samples (708 and 55,246 in 1.0.0), America 425 and 21,051 (404 and 19,796), Asia 27 and 1,254 (24 and 1,113). Taxa rise to 677 in Europe (635), 573 in America (564) and 125 in Asia (104).
- **Vegetation plots.** Unchanged in all three windows: the same datasets, samples and number of taxa. In America, 18,520 of the 29,701 plots (15,932 from VegBank and 2,588 from CVS, both BIEN sources) hold only presence records without an abundance, in both releases. The extraction returns them with an empty community, so the America modern models used 11,181 plots, and will use the same plots on 2.0.0.
- **Traits.** Trait values in the windows: America 8,711,891 (8,713,471 in 1.0.0), Europe 232,843 (262,562; a fall of 11 %, mostly TRY values: 188,916 against 217,765), Asia 1,116 (1,117). The release notes name two causes: duplicated measurements, including BIEN records that copy TRY, are removed, and TRY values now come from TRY's standardised values. Taxa with trait values rise in America (3,342 against 3,228) and Europe (4,959 against 4,743). Across the whole database, 2,655 of 28,272 TRY trait datasets have no coordinates in 2.0.0 (4,410 of 32,342 in 1.0.0), so they lie in no window.
- **The 0 ka slice.** Cores with a sample at 0 cal yr BP: Europe 30 (26 in 1.0.0), America 20 (22), Asia 1 (1). Extraction keeps ages from 0 and the age interpolation does not extrapolate, so only these cores give a sample at 0 ka. Asia stays below `min_n_samples` (10), so its 0 ka exclusion in `temporal.yml` stays. Europe and America have enough cores; their 0 ka slices failed in 1.0.0 only because `bio4` was 0 there.
- **Present-day temperature seasonality (`bio4`).** At 0 ka, `bio4` was 0 at 99 % (America), 85 % (Asia) and 92 % (Europe) of the gridpoints of 1.0.0, and it is never 0 in 2.0.0 (minimum 98, 874 and 198 hundredths of a degree). At each gridpoint, the present-day value is close to that of 500 cal yr BP: the median ratio is 1.01, 1.00 and 0.98, and 90 % of gridpoints lie between 0.79 and 1.24.
- **All other climate values are unchanged.** Every value of the seven climate variables that both releases hold is identical, at every age and in every window. 2.0.0 holds more gridpoint samples in every window and at every age (1 % more in America, 6 % in Asia and 4 % in Europe), and no gridpoint sample of either release lacks a value. A vegetation sample can therefore be linked to a nearer gridpoint than in 1.0.0.
- **Precipitation.** One America gridpoint has present-day `bio12` at the storage limit of 6,553.5 mm, which is a lower bound; 1.0.0 has the same value. `bio18` is 0 at 247 America and 76 Europe gridpoint samples aged 500 to 13,000 cal yr BP, where the warmest quarter had less than 0.5 kg m⁻² and the source rounds to whole units; 1.0.0 has the same zeros, so the v1 models already had them. `bio19` is never 0 in the windows. The masked block of past precipitation (25° S to 5° N) lies outside every window.
